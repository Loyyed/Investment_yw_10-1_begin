### 用 Claude Code 搭建证券研究工作台

## 今天的课堂契约

今天要完成的是：

> **搭建一个能够持续开展证券研究的项目工作台：在这个工作台中研究过程可回溯，关键判断有证据，数据与结论可核验，出现错误时能够定位、修正并复盘**

课堂中使用 Agent（Claude code, Codex, workbuddy等）；不用 Agent 的同学也能沿人工路径完成同一套研究任务。

---

## 三节课的五个连续问题

```text
→ 怎样从零开始搭建工作台？
→ 怎样把研究任务准确地交给 Agent?
→ 怎样把年报放进工作台完成第一次研究任务？
→ 怎样用 Git 记录研究过程，让每一次修改都可追溯？
→ 怎样回到原始年报，对每一条研究主张进行证据核验？
```

每解决一个问题，工作台就增加一项能力，也留下一个可以核查，可以复现的成果。

## 人、Agent 和年报的分工

| 角色 | 主要作用 | 不能替代什么 |
| --- | --- | --- |
| 研究者（人） | 定义问题、限定材料、核验原文、解释机制、承担判断责任 | 不能用流畅的回答替代自己的核验与判断 |
| Agent | 在任务合同限定的原始材料中读取、定位、整理、提取线索、发现遗漏 | 不能替代原始证据，成为事实来源或投资决策者 |
| 年度报告 | 提供可定位与可核验的一手材料 | 不能自动证明商业逻辑、价值创造或投资结论 |

年报提供证据，Agent定位和处理证据，人提出问题，核验问题并承担最终判断责任

# 一、为什么需要研究工作台？

> 从“一次聊天”转向“一个可以持续研究、回溯和核验的项目现场”。

**本章产物：工作台结构草图。**

## 1.1 把年报直接丢进聊天框，够不够？

如果只是临时问几个问题，当然够。

但证券研究通常不是一次问答：材料会不断增加，任务会反复修改，研究可能跨越多个会话和 Agent，重要判断最终还必须回到原始证据。

这时，真正的问题就不再是“Agent 能不能回答”，而是：

> **怎样让整个研究过程始终处于可管理的状态？**

可以把这种管理问题归纳为四类：

| **失控类型**   | **典型问题**                         | **工作台的解决方式**             |
| -------------- | ------------------------------------ | -------------------------------- |
| **文件失控**   | 材料越来越多，放在哪里、用了哪一份？ | 分类保存原始材料、过程文件和输出 |
| **上下文失控** | 换一个会话或 Agent，又要从头解释     | 用项目说明和规则保存长期上下文   |
| **过程失控**   | 做过什么、改过什么、为什么改？       | 用任务记录和 Git 保存过程        |
| **证据失控**   | 结论从哪里来，能不能回到原文？       | 建立证据定位、核验和记录机制     |

> **研究工作台不是为了让 Agent 更聪明，而是为了让研究过程可管理、可追溯、可核验。**

---

## 1.2 工作台解决的不是“让 Agent 更聪明”

工作台解决的是五个更基础的问题：

```text
材料在哪里？
→ 年报、公告、数据和研究笔记如何组织？

规则和边界是什么？
→ Agent 可以做什么、使用哪些材料、遵守哪些项目规则？

当前任务是什么？
→ 这一次要完成什么，输入、输出和验收标准是什么？

研究过程如何留下来？
→ Agent 做过什么、研究者改过什么，如何记录和回看？

结论如何回到证据？
→ 一条研究结论能否回到原始年报，找到对应的页码、表格和原文？
```

工作台不是为了让Agent更聪明，而是为了让**材料有位置，任务有边界，过程有记录，结论有证据**。

---

## 1.3 什么是年报研究工作台？

它是一个围绕具体研究对象或研究问题建立的项目化协作环境**。**它把材料、规则、任务、过程、证据和版本组织在同一个项目中，让研究者和 Agent 可以持续协作。注：为了上课方便，我们暂且称之为“年报研究工作台”，具体叫什么不重要。

它至少包含：

- 清晰易懂的项目根目录。什么叫“清晰易懂”？项目设置你看一眼便能懂，Agent也能懂，对人和机器都很友好。
- 长期有效的项目规则。适用于该项目研究，持续更新迭代，且长期有效的研究规则和Agent行为边界（或者说Agent的行为规范）。在一些大型项目中，为了减轻claude.md的负担，研究者会将部分规则和行为边界分解出来，叫法多种多样，例如rules/, specs/ 等。
- 可追溯的原始材料 `sources/`。统一保存和管理一手原始资料，并保持原文不被改写。
- 结构化任务与过程底稿 `tasks/`、`work/`。每次任务有明确要求，研究过程可以回看。
- 人工核验的证据记录。重要主张能够回到年报原文（或一手原始材料）进行人工核验。
- 版本历史。阶段成果和关键修改能够保存、比较和恢复。

## 1.5 课堂实操 1：画出你的工作台

拿出纸笔画出一张**年报研究工作台草图**，至少标明：

- **原始材料**放在哪里；
- **项目规则**放在哪里；
- **研究问题与任务合同**放在哪里；
- **过程底稿与待核验线索**放在哪里；
- **人工核验后的证据记录**放在哪里；
- **阶段成果与最终输出**放在哪里；
- 哪些内容应当**保持原始状态**，哪些内容可以在研究过程中持续修改。

不是要画Agent的workflow，而是要画“研究发生在哪里？”

### 1.5.1 示例：一家公司的年报研究工作台

假设研究对象是 **A 公司 2024 年年度报告**，可以先画出这样的项目空间：

```
annual-report-workbench/
│
├── README.md              # 项目目的与目录说明
├── CLAUDE.md              # 项目规则与 Agent 行为边界
│
├── sources/               # 原始材料：保持原始状态
│   └── A公司_2024年报.pdf
│
├── tasks/                 # 研究问题与任务合同
│   └── 第一次任务合同.md
│
├── work/                  # 过程底稿：持续修改
│   ├── notes.md
│   └── pending-checks.md
│
├── evidence/              # 人工核验后的证据记录
│   └── evidence-log.md
│
├── outputs/               # 阶段成果与最终输出
│   └── first-analysis.md
│
└── .git/                  # 版本、差异与提交历史
```

#### 1.5.1.1 你需要在草图中清晰地表达什么？

目录名称不需要与示例完全一样，但是它能够回答：

**材料在哪里？规则在哪里？任务在哪里？过程在哪里？证据在哪里？结果在哪里？**

同时区分两类内容：

- `sources/`：保存原始材料，**保持原始状态**；
- `tasks/`、`work/`、`evidence/`、`outputs/`：随着研究推进，**可以持续增加和修改**。

> 验收标准：换一个人或 Agent 进入这个项目，也能迅速知道材料在哪里、规则是什么、当前任务是什么，以及到哪里查看过程、证据和结果。

## 1.6 检查点 1：你的工作台草图合格吗？

画完后，用四个问题检查：

1. **原始材料**是否有独立的存放位置？
2. **项目规则和任务合同**是否有明确的位置？
3. **过程底稿、证据记录和阶段成果**是否分别存放？
4. 哪些内容应保持原始状态、哪些内容可以修改，是否区分清楚？

> 四个问题都能回答，你就完成了一个最小可用的工作台结构设计。

# 二、怎样建立年报研究工作台？

> *把工作台草图落地成真实的项目目录和项目规则。*

预期产物：最小项目目录、**`**README.md**` **与** `**CLAUDE.md**` **初稿。**

## 2.1 工作台从一个项目根目录开始

```
annual-report-workbench/
├── README.md
├── CLAUDE.md
├── .gitignore
├── sources/
├── tasks/
├── work/
├── evidence/
└── outputs/
```

目录名称可以根据具体项目灵活调整，但几个核心功能应当保留：

**原始材料、项目规则、任务合同、过程底稿、证据记录和阶段成果，都有明确的位置。**

## 2.2 `sources/`：保存原始材料

这里存放：

- 课程指定的年度报告 PDF；
- 经批准使用的公告、审计报告等正式披露；
- 为检索方便生成的 Markdown 等转换文件。

基本规则：

> **原始材料保持原始状态。** 不改写原文，不用摘要替代原文，也不把未经确认的外部资料混入其中。

原始资料的转换文件只是检索辅助，最终核验仍应回到原始披露。

## 2.3 `tasks/`：保存任务合同

这里存放每一次研究任务的明确要求，包括：

- 要回答的研究问题；
- 可以使用哪些材料；
- Agent 需要完成什么；
- 输出写到哪里；
- 什么条件下算任务完成。

任务合同的作用，是把“帮我看看这份年报”变成一个**边界明确、可以执行和验收的研究任务**。

## 2.4 `work/`：保存过程底稿

这里存放研究过程中产生的临时性内容，例如：

- 阅读笔记；
- Agent 提取的待核验线索；
- 关键词、候选页码和表格位置；
- 人工修正记录；
- 失败记录和待确认问题。

`work/` 中的内容允许不完整，也允许出错。

> **过程底稿的价值是留下研究过程，而不是提前写出最终结论。**

## 2.5 `evidence/`：保存证据核验记录

这里存放经过人工核验的重要证据，例如：

- 证据对应的年报名称、报告期和具体页码；
- 对应的表格、段落和原文；
- 数据的单位和统计口径；
- 证据能够支持什么和不能支持什么；
- 尚未确认或存在冲突的事项。

这里需要特别区分：

> **Agent 找到的是待核验线索；经过人工核验后，才能形成证据记录。**

因此，`evidence/` 不是简单存放 Agent 输出的地方，而是保存**经过核验的研究证据**。

## 2.6 `outputs/`：保存阶段成果

这里存放：

- 年报研究任务的阶段成果；
- 课堂提交材料；
- 后续形成的分析报告或研究报告章节。

阶段成果应当尽可能说明：

- 使用了哪些原始材料；
- 主要判断依据的是哪些证据；
- 哪些内容已经核验；
- 哪些内容仍然存在不确定性，需要继续检查。

> `outputs/` 只保存阶段成果；研究过程中的笔记、线索和临时文件统一放在 `work/`

## 2.7 `README.md`：项目说明

`README.md` 主要给进入项目的人阅读。

它回答几个基本问题：

- 这个项目研究什么？
- 使用哪些主要材料？
- 每个目录分别存放什么？
- 当前项目有哪些主要任务和成果？

它的作用是让第一次进入工作台的人，能够快速理解这个项目，而不是从一堆文件开始猜。

## 2.8 `CLAUDE.md`：项目规则

`CLAUDE.md` 主要告诉 Agent 在这个项目中应该如何工作。

它明确：

- 可以使用哪些材料；
- 哪些文件应保持原始状态；
- 哪些目录可以产生或修改文件；
- 如何处理待核验线索和证据；
- 输出结果应该保存在哪里；
- 遇到材料不清、证据不足或任务冲突时应该如何处理。

> `**CLAUDE.md**` **不是一次性的提示词，而是作用于整个项目的长期规则。**

## 2.9 `.gitignore`：哪些文件不进入版本历史？

并不是工作台中的所有文件都需要进入 Git。

通常可以排除：

- 临时文件和编辑器缓存；
- 密码、Token 和环境配置文件；
- 不应进入项目版本历史的个人资料；
- 根据课程或项目要求无需提交的大型文件或重复文件。

`.gitignore` 的作用很简单：

> **明确哪些文件不进入版本历史。**

 Git 如何记录修改、比较差异和恢复版本，将在后面的 Git 实操中完成。

## 2.10 工作台中的人机分工

| **位置**    | **研究者（人）**   | **Agent**                    | **基本规则**                           |
| ----------- | ------------------ | ---------------------------- | -------------------------------------- |
| `sources/`  | 阅读、引用和核验   | 在任务范围内读取和定位       | 原始材料保持原始状态                   |
| `tasks/`    | 定义并确认任务     | 理解任务、指出信息缺口       | 不擅自改变研究问题                     |
| `work/`     | 记录、修正和补充   | 整理过程底稿并提取待核验线索 | 过程底稿不是最终证据                   |
| `evidence/` | 核验并确认重要证据 | 协助整理证据记录             | 待核验线索经人工核验后才能成为证据记录 |
| `outputs/`  | 审核并形成最终判断 | 根据任务要求整理阶段成果     | 重要判断应有相应证据支持               |

> **Agent 可以帮助寻找和整理证据，但从“待核验线索”到“证据记录”，必须经过人工核验。**

## 2.11 教师演示：从空目录到最小工作台

演示的重点不是展示命令有多快，而是把前面设计的工作台真正建立起来。

教师现场完成：

1. 建立年报研究的**项目根目录**；
2. 建立 `sources/`、`tasks/`、`work/`、`evidence/` 和 `outputs/`；
3. 创建项目说明 `README.md` 和项目规则 `CLAUDE.md`；
4. 将年报放入 `sources/`，说明为什么**原始材料应保持原始状态，并与过程底稿和阶段成果分开存放**；
5. 查看完整目录树，确认**原始材料、任务合同、过程底稿、证据记录和阶段成果**都有明确的位置。

演示完成后，学生使用课堂提供的模板建立自己的最小工作台，并检查各类文件是否放在正确的位置。

> **这一环节的目标不是记住命令，而是把“工作台草图”变成一个真实、可使用的研究项目。**

## 2.12 课堂实操 2：创建并检查自己的工作台

现在，把上一环节的工作台草图落地成真实的项目目录。

完成以下操作：

- 使用课堂模板，或建立功能相同的项目目录；
- 打开 `README.md`，填写项目的**研究对象、使用材料和本课程的学习任务**；
- 打开 `CLAUDE.md`，阅读并确认**项目规则和 Agent 行为边界**；
- 将原始年报放入 `sources/`；
- 查看完整目录树，确认**原始材料、任务合同、过程底稿、证据记录和阶段成果**都有明确的位置。

**人工路径：**不使用 Agent 的同学，可以手工完成相同的目录和文件创建任务。

> **完成标准：工作台已经真实存在，并能够开始承接第一次年报研究任务。**

## 2.13 最小示例

### 2.13.1 `README.md`

```
# A 公司年报研究

## 项目目的

基于 A 公司年度报告开展证券研究，并保留可回溯、可核验的研究记录。

## 项目结构

- `sources/`：原始材料
- `tasks/`：任务合同
- `work/`：过程底稿
- `evidence/`：证据记录
- `outputs/`：阶段成果
```

`README.md` 到这里就够了。

它只回答两个问题：

**这是一个什么项目？**
**项目里的东西放在哪里？**

### 2.13.2 `CLAUDE.md`

```
# 项目规则

## 工作原则

- 执行任务前，读取 `tasks/` 中对应的任务合同。
```

## 2.14 检查点 2：工作台建好后，为什么还不能直接开始？

项目目录和 `CLAUDE.md` 已经告诉 Agent：

**材料在哪里、项目规则是什么、在这个项目中应该怎样工作。**

但它仍然不知道**这一次任务具体要完成什么**：

- 要回答什么研究问题；
- 这一次使用哪些材料；
- 需要完成哪些具体工作；
- 应该形成什么样的阶段成果；
- 满足什么条件才算任务完成。

这些内容不能依靠 Agent 自己猜测，而需要写进一份明确的**任务合同**。

> **项目规则规定“平时怎么做”，任务合同规定“这次做什么”。**

## 3.1 先回顾第 1 课：我们已经解决了什么？

第 1 课已经建立了三项共同要求：

1. **定义问题**：公司信息不等于证券判断；先明确要研究什么；
2. **限定材料**：不混入报告期外信息，不把管理层叙事直接写成结论；
3. **核验证据并承担判断**：Agent 的输出不是事实，也不能替代研究者的判断。

本课要解决的是：**这些要求在一个持续研究的项目中放在哪里，怎样变成可执行的工作。**

## 3.2 两课之间的承接：从研究要求到可执行任务

```text
第 2 课
```

## 3.3 项目规则与任务合同：分别解决什么问题？

| 文件或概念 | 它规定什么？                                                 | 在本课中的位置     |
| ---------- | ------------------------------------------------------------ | ------------------ |
| 项目规则   | 在整个项目中持续适用的材料边界、文件读写规则、证据标准与 Agent 行为边界 | `CLAUDE.md`        |
| 任务合同   | 本次任务要解决什么问题、使用哪些原始材料、遵守什么边界、过程记录写到哪里、形成什么阶段成果，以及如何验收 | `tasks/第一次任务合同.md` |

> **项目规则规定“这个项目里一直怎么做”；任务合同规定“这一次具体做什么、做到什么程度算完成”。**

两者解决的是不同层次的问题。项目规则长期作用于整个研究项目，不随某一次任务结束而失效；任务合同则针对当前任务，把已经明确的研究问题进一步落实为**可以执行、可以记录和可以验收的具体工作**。

因此，任务合同是研究问题进入工作台之后，从“我要研究什么”走向“这一次具体怎么做”的连接点。

## 3.4 一份任务合同要把什么写清楚？

一份任务合同，至少要把六件事写清楚：

| 要素               | 要回答的问题               | 任务合同中要写清楚什么                                       |
| ------------------ | -------------------------- | ------------------------------------------------------------ |
| **目标**           | 这一次具体要完成什么？     | 把研究问题收窄为本次可以执行的任务                           |
| **原始材料**       | 这一次允许使用哪些材料？   | 明确文件、报告期和版本，限定材料范围                         |
| **任务边界**       | 哪些事情不能做？           | 明确不读取什么、不判断什么、不修改什么                       |
| **过程底稿**       | 研究过程记录在哪里？       | 指明确检索路径、待核验线索和修正记录保存到哪个过程文件       |
| **阶段成果**       | 任务完成后要留下什么？     | 明确输出内容、格式和保存到哪个成果文件                       |
| **验收与证据核验** | 怎样判断这项任务已经完成？ | 回到原始材料，核对页码、表名、报告期、单位、统计口径以及必要的脚注和说明 |

## 3.6 Agent 如何接手一次任务？

任务合同写清楚后，Agent 才能在其中规定的范围内接手辅助工作。这里的“接手”是先阅读、理解和**复述**合同，不是立即读取真实年报或提取其中的信息。它不重新定义问题，也不将线索写成事实。

```text
研究者：定义问题 → 限定材料 → 核验证据 → 承担判断

Agent：读取项目规则与任务合同
→ 定位原始材料中的章节、表格或关键词
→ 整理检索路径和候选表格结构
→ 提取待核验线索
→ 发现缺少页码、期间、单位、口径或上下文的地方
```

Agent 交回的不是“答案”，而是供研究者继续检查的过程记录，包括可能对应目标信息的页码、章节或表格位置，从原文中提取的候选数值或文字，以及尚未确认的缺口、冲突和遗漏。

这里的“候选”是指：**Agent 已经在原始材料中找到一个可能正确的结果，但研究者尚未完成原文核验。**

因此，在研究者回到 PDF 原文，核对页码、表名、报告期、单位、口径以及必要说明之前，任何候选数值、候选位置或候选表述，都只能作为**待核验线索**，不能直接写成已经确认的事实。。

## 4.2 先定位，再提取

第一次读取年报时，先建立清楚的定位路径，再提取具体信息。

本次任务按照以下顺序推进：

```
确认任务合同与指定年报
→ 定位目标报表或章节
→ 确认表名、报告期和单位
→ 提取候选数值及其对应位置
→ 记录检索过程
→ 形成待核验线索
```

以本次任务为例，需要定位的是**营业收入**和**归属于上市公司股东的净利润**。先找到对应的合并利润表，再记录候选数值及其位置。

检索过程写入 `work/notes.md`；已经定位但尚未核验的具体信息写入 `work/pending-checks.md`。

> **这一阶段只完成从原始年报到待核验线索的定位与提取，不把候选信息直接写成已经确认的** `**Fact**`**。**

## 4.3 第一次任务的交付标准

第一次任务结束时，应形成**可以进入下一步证据核验的过程底稿和待核验线索**。

交付前检查：

- `work/notes.md` 是否能够看出信息是怎样被定位到的；
- `work/pending-checks.md` 是否已经记录本次任务需要进一步核验的候选信息；
- 每条待核验线索是否具有足够的原始年报定位信息，能够在后续重新找到；
- 尚未确认的内容是否仍明确保留为待核验状态，而没有被写成 `Fact`。

> **完成这些记录，第一次年报定位与提取任务即告结束；下一步再进入证据核验。**

## 4.4 待核验线索怎样记录？

`work/pending-checks.md` 用来记录已经定位、但尚未完成证据核验的具体线索。

每条待核验线索至少应该记录以下字段：

| 字段             | 作用                                             |
| ---------------- | ------------------------------------------------ |
| 指标名称         | 明确当前定位的是什么信息                         |
| 候选数值         | 记录从年报中提取的候选信息                       |
| 候选位置         | 记录页码、表名、章节或段落等定位信息             |
| 报告期及比较信息 | 明确数值对应的报告期；原表存在比较数据时一并记录 |
| 单位             | 避免元、千元、万元等单位混淆                     |
| 口径             | 标记合并、母公司或其他相关口径                   |
| 核验重点         | 标记后续证据核验时需要特别检查的事项             |

例如：

```
指标名称：营业收入
候选数值：……
候选位置：第 X 页，合并利润表
报告期：2024 年度
比较信息：原表同时列示上期金额
单位：……
口径：合并口径
核验重点：确认页码与表格单位是否准确
```

## 4.5 教师演示：完成一次年报定位与提取

教师现场执行第一次年报任务：

1. 打开项目规则和任务合同；
2. 读取任务合同指定的原始年报；
3. 定位合并利润表；
4. 搜索营业收入和归属于上市公司股东的净利润；
5. 记录检索路径、候选位置以及过程中遇到的问题；
6. 将检索过程写入 `work/notes.md`；
7. 将候选信息整理到 `work/pending-checks.md`。

演示过程中重点检查：

- 是否始终使用任务合同指定的材料；
- 候选信息是否保留了足够的原始年报定位；
- 信息不完整时是否明确保留为待核验状态；
- 过程底稿和待核验线索是否写入正确的位置。

> **本次演示到形成待核验线索为止，不进入证据核验。**

## 4.6 课堂实操：完成第一次年报任务

现在按照相同的流程完成自己的第一次任务。

至少完成：

- 定位营业收入或归属于上市公司股东的净利润中的一项；
- 记录信息是怎样被找到的；
- 提取候选数值及其对应位置；
- 将检索过程写入 `work/notes.md`；
- 将候选信息写入 `work/pending-checks.md`。

完成后，对照 4.3 的交付标准和 4.4 的记录字段，检查自己的过程底稿和待核验线索是否完整。

未使用 Agent 的同学，可以从目录、表格标题和关键词检索开始，完成相同的定位、提取和记录任务。

## 4.7 检查第一次任务：研究过程能否回看？

第一次任务完成后，交换工作台进行快速检查：

- 是否使用了任务合同指定的原始年报；
- `work/notes.md` 是否能够看出信息是怎样被定位到的；
- `work/pending-checks.md` 中的线索是否能够重新回到原始年报；
- 尚未确认的信息是否仍然保留为待核验状态；
- 是否出现了超出当前任务范围的解释或判断。

发现问题后，回到相应的过程文件完成修正。

到这里，工作台已经留下了第一次真实研究任务的**过程底稿和待核验线索**。但研究过程还存在一个新的问题：

> **如果任务被修改、文件被改错，或者我们想知道前后两个版本究竟发生了什么变化，怎样把这些修改保存下来，并在需要时重新查看？**

下一部分开始解决这个问题：**用 Git 记录研究过程和版本历史。**

## 5.0 开始前：安装 Git 并确认它可以工作

### Git 是什么？GitHub 又是什么？

先把两个容易混淆的词分开：

| 名称 | 这节课中的含义 |
| --- | --- |
| **Git** | 安装在自己电脑上的版本管理工具。它可以在本地记录文件的历史，完全离线也能使用。 |
| **GitHub** | 存放 Git 仓库的云端网站，适合备份和协作。本课不连接 GitHub，也不要求注册账号。 |

可以把 Git 想成工作台旁边的“研究档案柜”：项目文件仍在原来的文件夹里，Git 只是另外记录每一次经过检查的版本快照。Git 不会自动判断研究结论是否正确，也不会替你核验年报。

### macOS 学生的安装路径

本课只需要 Git，不需要先安装 Homebrew、GitHub Desktop 或其他图形化工具。先打开 **终端（Terminal）**：按 Command + 空格，输入“终端”，然后按回车。

在终端输入：

~~~bash
git --version
~~~

如果看到类似 git version 2.x.x 的版本号，说明 Git 已经可以使用，直接进入下一步。

如果提示找不到命令，输入：

~~~bash
xcode-select --install
~~~

系统会弹出安装窗口。选择“安装”，等待完成后关闭并重新打开终端，再次运行 git --version。安装过程中不需要理解 Xcode；我们只使用其中提供的命令行工具。

### 安装后的三个验收动作

在终端依次输入：

~~~bash
git --version
pwd
~~~

第一行确认 Git 存在；第二行显示“当前所在文件夹”。Git 命令作用于当前文件夹及其子文件夹，所以在操作前一定要先确认自己已经进入本组的年报研究工作台。若当前路径不对，不要急着运行 git init，先回到正确的项目文件夹。

> **零基础提示：** 终端中的路径不是网页地址。pwd 只是“告诉我现在在哪”；cd 文件夹路径 才是“进入某个文件夹”。如果不熟悉路径，可以在 VS Code 中打开项目文件夹，再从“终端 → 新建终端”启动，通常会自动进入项目根目录。

本课的安全边界是：只在自己的年报研究项目中使用本地 Git；不把年报项目推送到远程网站，不把密钥、密码或个人隐私文件加入版本历史。

### Windows 学生的安装路径

Windows 学生安装的是 **Git for Windows**。课堂不要求安装 WSL（Windows Subsystem for Linux），也不要求先安装 GitHub Desktop；安装 Git for Windows 后，Git Bash 和 VS Code 都可以使用同一套 Git 命令。

1. 打开浏览器，进入 Git for Windows 官方下载页：<https://git-scm.com/download/win>，下载与你的 Windows 系统匹配的安装程序。
2. 双击安装程序，安装过程中大多数选项保持默认即可。遇到“选择默认编辑器”时，若不确定，选择 **Use Visual Studio Code as Git's default editor**（电脑已安装 VS Code 时）或保留默认选项。
3. 遇到“PATH 环境”选项时，保持推荐的 **Git from the command line and also from 3rd-party software**，这样 VS Code 和其他程序也能找到 Git。
4. 安装完成后，在开始菜单打开 **Git Bash**；也可以打开 VS Code，在“终端 → 新建终端”中选择 Git Bash。

在 Git Bash 中先验收：

~~~bash
git --version
pwd
~~~

如果看到版本号，说明安装成功。Git Bash 中的路径通常显示为 /c/Users/你的用户名/...，这是正常的；它对应 Windows 文件资源管理器中的 C:\Users\你的用户名\...。在 Windows Terminal 或 PowerShell 中，路径可能显示为 C:\Users\你的用户名\...，但后面的 Git 命令相同。

> **Windows 的课堂建议：** 为减少路径和命令差异，课堂演示优先使用 VS Code 的 Git Bash 终端。不要在同一个项目里一会儿用 Git Bash、一会儿用 PowerShell 去改写路径；如果必须使用 PowerShell，只需记住 Git 命令不变，路径写法按 PowerShell 的显示为准。

#### Windows 路径与常见小问题

| 情况 | 处理方法 |
| --- | --- |
| 找不到 Git 命令 | 关闭并重新打开 Git Bash 或 VS Code；仍找不到时重新运行安装程序，确认 PATH 选项选择了“Git from the command line…” |
| 不知道项目路径 | 在 VS Code 中用“文件 → 打开文件夹”打开年报工作台，再用“终端 → 新建终端”；终端通常会自动定位到项目根目录 |
| 路径中有空格或中文 | 在命令中给路径加双引号，例如 cd "C:\Users\学生\年报研究工作台"；更稳妥的做法是直接在 VS Code 中打开该文件夹 |
| Git Bash 显示路径与资源管理器不同 | 不要手动改写路径；/c/Users/... 就是 C:\Users\... 的 Git Bash 表示 |
| Git 报文件名大小写或换行差异 | 不要急着删除文件或重新建仓，先运行 git status，把提示记录下来再处理 |

Windows 学生完成上面的验收后，直接从 5.1 开始学习；初始化仓库、查看状态、阅读差异、暂存、提交、查看历史和回滚的命令与 macOS 完全相同。

## 5.1 Git 在研究中的四个问题

| Git 概念 | 研究中回答的问题 |
| --- | --- |
| `status` | 我现在改了什么？ |
| `diff` | 两个版本之间具体哪里不同？ |
| `commit` | 这组已检查的修改，何时、因何被保存？ |
| `revert` | 发现错误后，怎样撤回修改但保留历史？ |

Git 不是“自动保存正确答案”；它是保存可解释过程的工具。

## 5.2 最小版本历史循环

完成一次小任务后，不要立即提交。先检查发生了什么变化，再决定哪些修改值得进入版本历史。

```
完成一次小任务
→ git status：查看哪些文件发生了变化
→ git diff：阅读具体修改
→ 人工检查：确认修改符合任务要求，没有误改原始材料或混入不应保存的内容
→ git add：选择本次准备保存的修改
→ git diff --staged：再次检查即将提交的内容
→ git commit：将这一组已经检查的修改保存为一个版本
```

这里最重要的不是记住 Git 命令，而是形成一个习惯：

> **先看变化，再做检查；先确认要保存什么，再形成一次提交。**

Agent 完成文件写入，只意味着“文件发生了变化”，并不意味着这些变化已经通过研究者检查。

因此：

> **不要因为 Agent 已经完成任务，就跳过** `**diff**` **和人工审查直接提交。**

### 5.2.1 用一个“档案柜”理解 Git 的三个位置

初学时不必背诵内部结构，但要知道一次提交前有三个位置：

| 位置 | 通俗理解 | 研究中的问题 |
| --- | --- | --- |
| **工作区（working tree）** | 你正在编辑的文件夹 | 我刚才改了什么？ |
| **暂存区（staging area）** | 准备放进下一张快照的“待装箱区” | 这次究竟要保存哪些文件？ |
| **提交（commit）** | 已装箱、贴上说明并封存的快照 | 这组修改何时、为什么被保存？ |

所以 git add 不是“保存”，而是把指定修改放进下一次提交；真正形成版本节点的是 git commit。这也是为什么提交前还要再看一次 git diff --staged。

### 5.2.2 第一次建仓与第一次提交：逐步照做

只对**自己的年报研究工作台根目录**执行下面的操作。每一步都先看屏幕返回的内容，再继续下一步。

~~~bash
# 1. 确认当前所在目录
pwd

# 2. 建立本地 Git 仓库（一个项目只做一次）
git init

# 3. 查看当前状态
git status

# 4. 只把本次准备保存的文件放入暂存区
git add README.md CLAUDE.md tasks/ work/

# 5. 查看“即将提交”的具体差异
git diff --staged

# 6. 确认无误后，形成第一条版本记录
git commit -m "第2单元：保存第一次年报研究工作台"
~~~

如果本次只修改了一个文件，就只写那个文件的路径，例如 `git add work/notes.md`。初学时不要直接使用 `git add .`：它会把当前目录下所有未忽略的修改一并放入暂存区，容易把临时文件、错误文件甚至不应保存的材料一起提交。

### 5.2.3 每次修改后的标准操作

完成一次小任务后，建议按下面的固定顺序操作：

~~~bash
# 查看哪些文件发生了变化
git status

# 查看尚未放入暂存区的修改
git diff

# 选择本次要保存的文件
git add <文件路径>

# 再看一次将要提交的内容
git diff --staged

# 形成版本节点；备注要写“做了什么”
git commit -m "第2单元：补充营业收入待核验线索"
~~~

尖括号里的内容是占位符，实际输入时要换成真实路径，不要把尖括号一起输入。git status 是总览，git diff 是逐行比较，git diff --staged 是提交前的最后检查。

### 5.2.4 查看历史、暂存错误与安全恢复

提交之后，可以用以下命令回看已经保存的研究节点：

~~~bash
# 用一行显示每个版本
git log --oneline

# 查看最近一次提交具体改了什么
git show --stat --oneline HEAD
~~~

如果不小心把文件放进了暂存区，但还没有提交，可以撤回“待装箱”状态，文件本身不会被删除：

~~~bash
git restore --staged <文件路径>
~~~

如果已经提交，后来发现这次提交不应该保留，课堂上优先使用**保留历史的回滚提交**，而不是抹掉历史：

~~~bash
git revert <提交编号>
~~~

提交编号可以从 git log --oneline 的第一列复制。git restore <文件路径> 会丢弃该文件尚未提交的修改，使用前必须确认这些修改确实不需要；本课不讲 git reset --hard，也不要求学生使用强制回滚。

### 5.2.5 不想记命令时：用自然语言让 Agent 协助，但仍由人检查

也可以在 Claude Code、Codex 或其他课堂允许的 Agent 对话中说：

~~~text
请先运行 git status 和 git diff，告诉我本次具体改了哪些文件。
不要直接提交。等我确认后，只把 `work/notes.md` 放入暂存区，再展示 `git diff --staged`。
~~~

看清差异后，再说：

~~~text
差异符合本次任务，请提交这一组修改，备注为“第2单元：保存第一次年报研究记录”。
~~~

Agent 可以代为输入命令，但不能代替你决定哪些修改正确。任何涉及删除、丢弃未提交修改、回滚或远程推送的请求，都必须先停下来阅读影响范围并明确确认。

### 5.2.6 常见提示与处理方法

| 终端提示 | 它通常意味着什么 | 初学者怎么处理 |
| --- | --- | --- |
| git: command not found | Git 尚未安装或终端还没刷新 | 按 5.0 的步骤安装，重新打开终端，再运行 git --version |
| not a git repository | 当前文件夹不是已经建仓的项目根目录 | 先运行 pwd，在正确项目根目录运行一次 git init |
| nothing to commit, working tree clean | 当前没有新的未提交修改 | 这是正常提示，说明最近的修改已经保存，或文件还没有发生变化 |
| Changes not staged for commit | 文件改了，但还没有放入暂存区 | 先看 git diff，确认后运行 git add <文件路径> |
| Changes to be committed | 文件已经在暂存区，等待提交 | 先看 git diff --staged，确认后再 git commit |

遇到看不懂的红色报错，不要反复输入命令，也不要直接删除 .git 文件夹。先把完整提示复制到 work/notes.md，记录发生时间和刚才执行的命令，再请教师或 Agent 在不改变文件的前提下解释原因。

## 5.3 什么是一条有意义的提交？

一次 `commit` 应当对应一组**已经检查过、能够说明具体研究进展的修改**。

不推荐的提交说明写法：

```
更新
final
改了一下
最新版
```

这些说明无法告诉未来的自己：**究竟完成了什么研究工作。**

更好的提交说明应该直接描述本次保存的研究进展。

例如：

```
docs(unit2): add first annual-report extraction record
```

也可以直接使用中文：

```
第 2 单元：保存第一次年报定位与提取记录
```

如果本次修改更具体，也可以写成：

```
第 2 单元：补充营业收入待核验线索及检索记录
```

好的提交说明不需要很长，但应当让未来的自己能够回答：

> **这个版本为什么值得被单独保存？**

因此，一次好的 Git 提交通常同时满足两个条件：

1. **修改有明确边界**：这一组文件共同完成了一项可以说明的研究任务；
2. **提交说明有明确含义**：能够说明这一次保存了什么研究进展。

> **Git 提交不是给文件编号，而是在研究过程中留下一个有意义的版本节点。**

## 5.6 课内互检：研究过程能否被别人接手和检查？

完成第一次年报任务和 Git 提交后，不急着进入下一部分。先交换工作台，检查这套研究过程是否真的能够被别人理解、复查和继续使用。

请用 8 分钟完成：

1. **交换工作台**：同学们互看项目目录、任务合同、过程底稿和第一次 Git 提交；
2. **检查一处风险**：试着找出一处文件位置错误、任务边界不清、待核验线索被误写成事实，或版本记录不完整的问题；
3. **回到对应文件修正**：根据问题回到 `tasks/`、`work/` 或其他相应位置修改，而不是只改最终输出；
4. **再次查看差异**：使用 `git status` 和 `git diff` 检查这次修正具体改变了什么；
5. **决定是否形成新的版本节点**：如果这次修正构成了一项完整、已经检查过的研究进展，再形成一次新的 `commit`。

如果检查过程中发现问题暂时无法解决，就把它明确记录在 `work/notes.md` 或相应的待核验文件中。

**互检的目的不是证明工作台没有错误，而是验证：错误出现之后，我们能否定位它、修正它，并留下可回看的记录。**

# 六、回到年报，完成证据核验

> 工作台保存过程；证据核验决定一句话能否站住。

本章产物：**证据核验记录、`Unknown` 清单与红队意见**。

---

## 6.1 先分清三层：主张、证据与判断

| 层次 | 例子 | 本课要求 |
| --- | --- | --- |
| 主张 | “2024 年营业收入为……” | 必须可检查 |
| 证据 | 年报版本、页码、表名、原文、单位和期间 | 必须回到一手披露 |
| 判断 | “收入变化说明了什么” | 与事实分开，写出依据与边界 |

Agent 可以协助定位线索；是否成为证据，由人工核验决定。

---

## 6.3 第一步：把主张写得足够小

不写：

> 贵州茅台盈利能力很强。

先写：

> 贵州茅台 2024 年年度报告中披露的归属于上市公司股东的净利润是多少？位于哪张表、哪个报告期、采用什么单位？

主张越小，越容易定位、核验和发现边界。

---

## 6.4 第二步：定位是开始，不是完成

定位线索可以来自：

- 年报目录；
- PDF 搜索；
- Markdown 检索稿；
- Agent 在任务合同限定的原始材料范围内提供的线索；
- 同伴的章节建议。

无论线索来自哪里，下一步都必须是：**打开原始年报 PDF。**

---

## 6.5 第三步：核验原文的六个问题

1. 是哪一份报告、哪个版本？
2. 在哪一页、哪张表、哪一段？
3. 报告期和比较期分别是什么？
4. 单位是元、千元、万元还是其他？
5. 是合并口径、母公司口径还是分部口径？
6. 表格脚注、会计政策或上下文是否限制了这条信息？

没有回答完六个问题，就不要写成已核验的 `Fact`。

---

## 6.6 第四步：交叉印证与冲突

同一问题可能需要比较：

- 管理层经营叙事；
- 合并财务报表；
- 财务报表附注；
- 审计报告；
- 治理、关联交易和风险披露。

交叉核验不是为了强行得到一致答案。发现期间、口径或解释冲突时，正确做法可能是保留 `Unknown`。

---

## 6.7 第五步：写入证据核验记录

| 必须字段 | 为什么 |
| --- | --- |
| 主张与类型 | 区分 `Fact`、解释、预测与未知 |
| 来源版本与精确定位 | 让其他人能回到同一位置 |
| 报告期、比较基数、单位、口径 | 防止数字脱离语境 |
| 原文或数值摘要 | 保留必要上下文 |
| 支持边界 | 避免过度推论 |
| 人工核验与剩余问题 | 记录责任和不确定性 |

---

## 6.8 第六步：判断状态，不要用一个词遮盖不确定性

| 状态 | 含义 |
| --- | --- |
| `Fact` | 已回到一手披露的精确位置核验 |
| `Interpretation` | 对事实的解释，仍可能有替代解释 |
| `Forecast` | 对未来的条件化判断 |
| `Decision` | 在价格、风险和约束下的行动选择 |
| `Unknown` | 未披露、未核验或无法裁决的内容 |

待核验线索在完成原文核验前，不应被写为 `Fact`。

---

## 6.9 教师演示：一条记录如何通过或失败？

### 6.9.1 通过

- 能定位到指定年报；
- 页码、表格、期间、单位与任务一致；
- 支持范围没有被夸大；
- 已写入证据核验记录。

### 6.9.2 失败或部分支持

- 找到的页码与报告版本不匹配；
- 数字单位或比较期间遗漏；
- 管理层解释被写成事实；
- 年报没有披露所需指标。

处理：修订、收窄主张或进入 `Unknown`。

---

## 6.10 课堂实操 6：每人核验两条记录，每组完成五条

个人任务：

- 一条容易确认的数字或表格记录；
- 一条包含期间、单位、口径或上下文问题的记录。

小组任务：

- 至少 5 条证据核验记录；
- 至少两类披露的交叉比较；
- 至少一条 `Unknown` 或待核验问题；
- 如果使用 Agent，记录人工如何接受、修正或拒绝线索。

---

## 6.11 红队质询：不攻击观点方向，只攻击研究质量

红队可以问：

- 这条主张能回到年报原文吗？
- 页码、表名、报告期和单位是否完整？
- 会计口径和比较基数是否一致？
- 管理层叙事是否被误当成事实？
- 有没有附注、审计或治理披露构成限制？
- 为什么这项问题还不能裁决？

---

## 6.12 原组裁决只有三种结果

```text
通过
  → 记录支持边界

修订后保留
  → 说明修改了什么、为什么修改

移入 Unknown
  → 说明缺少什么披露或为什么不能裁决
```

最好的课堂答案不一定是“全部通过”，而是能诚实说明证据强度和限制。

---

## 6.13 工作台与证据核验终于连接起来

```text
工作台结构
  保存任务、材料、过程、证据、输出和版本

证据核验流程
  决定一条主张能否从线索变成可追溯记录
```

一个没有工作台的核验过程难以复现；一个没有核验标准的工作台只是在整理文件。

# 七、整合产物与课堂验收

## 7.1 本组提交包

```text
工作台目录
+ README.md
+ CLAUDE.md
+ 第一次任务合同
+ 过程底稿与待核验线索
+ 阶段成果
+ 证据核验记录
+ 版本历史（Git 提交记录或等价版本记录）
+ Unknown 与红队意见
```

---

## 7.2 教师验收的四个问题

1. **结构**：资料、任务、过程、证据和输出是否放在正确位置？
2. **边界**：Agent 的材料范围、可写位置和禁止事项是否清楚？
3. **过程**：是否能看到任务、修改、差异和人工修正？
4. **证据**：是否能从至少一条主张回到年报 PDF 的精确位置？

这四个问题都能回答，工作台才真正开始服务证券研究。

---

# 八、复盘、边界与下一步

请独立完成 Exit Ticket：

1. 我的工作台保存了什么，而一次聊天保存不了什么？
2. 我今天最可靠的一条 `Fact` 位于年报哪里？它仍不能证明什么？
3. Agent 提供过哪条待核验线索？我为什么接受、修正或拒绝它？
4. 下一单元进入财务报表分析时，我还要追问什么？

> Agent 可以帮助你读取、定位、整理、提取线索和发现遗漏；但只有你能核验证据并承担判断。
